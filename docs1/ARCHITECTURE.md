# Архитектура

Как устроен агент и почему именно так. Решения, за которыми стоит история
отладки, вынесены в [`DECISIONS.md`](DECISIONS.md).

---

## 1. Общая схема

```
┌─────────────┐    задача текстом      ┌──────────────────────────────┐
│  Web UI     │ ─────────────────────► │        Agent Loop            │
│  / CLI      │ ◄───────────────────── │  (core/loop.py)              │
└─────────────┘   события, вопросы     └───────┬──────────────────────┘
                                               │
                       ┌───────────────────────┼───────────────────────┐
                       ▼                       ▼                       ▼
              ┌────────────────┐     ┌──────────────────┐    ┌─────────────────┐
              │ Context Manager│     │  Tool Registry   │    │  LLM Router     │
              │ компакция,     │     │   17 инструментов│    │ роль → модель   │
              │ снапшоты,      │     └────────┬─────────┘    │ + фоллбэк       │
              │ scratchpad,    │              │              └────────┬────────┘
              │ реестр действий│              ▼                       │
              └────────────────┘     ┌──────────────────┐             ▼
                                     │ Security Guard   │   ┌──────────────────┐
                                     └────────┬─────────┘   │ навигатор        │
                                              ▼             │ ↓ фоллбэк        │
                                     ┌──────────────────┐   │ ↓ другой провайд.│
                                     │ Browser          │   └──────────────────┘
                                     │ Controller       │
                                     │  + Snapshot      │
                                     └────────┬─────────┘
                                              │ CDP :9222
                                              ▼
                                  ┌───────────────────────────┐
                                  │  Реальный Chrome          │
                                  │  профиль пользователя     │
                                  │  видимое окно             │
                                  └───────────────────────────┘
```

Ключевая мысль: **агент не знает ничего ни про один сайт**. Он получает
описание текущего состояния страницы, набор инструментов общего назначения
и цель. Всё остальное — его решения в моменте.

## 2. Подключение к браузеру

Chrome запускается **отдельно от агента**, с открытым портом отладки и реальным
профилем пользователя:

```powershell
chrome.exe --remote-debugging-port=9222 --user-data-dir="$env:LOCALAPPDATA\browser-agent-profile"
```

Агент цепляется к нему:

```python
browser = await playwright.chromium.connect_over_cdp("http://127.0.0.1:9222")
```

Так закрываются сразу три требования задания:

| Требование | Как закрывается |
|---|---|
| Программное управление | Playwright поверх CDP |
| Persistent sessions | профиль живёт между запусками, пользователь логинится руками один раз |
| Видимый браузер | Chrome запущен как обычное окно, агент к нему только присоединяется |

Побочный, но важный эффект: не приходится бороться с антибот-защитой, потому
что это настоящий браузер с настоящей историей и настоящими куками. Отдельный
«чистый» Playwright-Chromium на крупных сайтах ловит капчу почти сразу.

**Docker.** Контейнер не может показать GUI и не видит профиль хоста, поэтому
Chrome остаётся на хосте, а в контейнер уезжает только агент:
`CDP_URL=http://host.docker.internal:9222`.

## 3. Слой снапшотов — ядро проекта

Задача: превратить страницу в 2–4k токенов, не потеряв ничего, что нужно
для принятия решения.

### 3.1 Сбор

Гибрид двух источников, потому что по отдельности они неполны:

- **AX-дерево** (`Accessibility.getFullAXTree` через CDP) даёт семантику: роль,
  доступное имя, состояние (checked, expanded, disabled). Но в нём нет
  координат, и оно молчит про кастомные `div`-кнопки без ARIA.
- **Обход DOM** (инъекция `js/collect.js`) даёт геометрию, видимость,
  вычисленные стили и достаёт то, что AX пропустил.

Обход идёт по всем фреймам и проникает в open shadow roots.

### 3.2 Фильтрация

Элемент попадает в снапшот, если он **интерактивен** и **реально видим**.

Интерактивность — по совокупности признаков, а не по списку тегов: роль из ARIA,
тег из `a/button/input/select/textarea`, обработчик клика, `tabindex >= 0`,
`cursor: pointer`, `contenteditable`.

Видимость — три проверки подряд:

1. непустой `getBoundingClientRect()`
2. не `display:none` / `visibility:hidden` / `opacity:0` по цепочке предков
3. **`document.elementFromPoint(cx, cy)` возвращает сам элемент или его потомка**

Третья проверка — самая ценная. Она бесплатно решает проблему перекрытий: если
поверх кнопки лежит куки-баннер или модалка, кнопка автоматически выпадает
из снапшота, а баннер в него попадает. Агенту не нужны хардкод-списки попапов —
он видит то же, что человек, и сам решает закрыть модалку.

Это не оптимизация, а способ не нарушить запрет на преднаписанные селекторы:
список «кнопок закрытия баннеров» был бы прямым нарушением
([`CONSTRAINTS.md`](CONSTRAINTS.md) §2).

### 3.3 Сжатие

- **Только видимая область ± один экран.** Остальное сворачивается в строку
  `↓ ещё ~40 элементов ниже, прокрутите`.
- **Схлопывание одинаковых соседей.** 50 карточек с идентичной структурой →
  3 первых + `× ещё 47 таких же`.
- Выкидываются классы, стили, инлайновые атрибуты, id вида `react-aria-1723`.
- Текст обрезается до 120 символов на элемент.

### 3.4 Формат `PageState`

То, что реально уходит в модель:

```
URL    https://example.test/search?text=AI+инженер
TITLE  Работа AI инженер
TABS   [0*] example.test — Работа AI  │  [1] mail.example.test — Входящие
SCROLL 1200 / 8400  (14%)
STATE  loaded

[e12] textbox  "Профессия, должность"  = "AI инженер"
[e13] button   "Найти"
[e18] combobox "Регион"  expanded=false
[e21] link     "AI Engineer — Компания А"     → /vacancy/12345
[e22] button   "Подать заявку"
[e29] link     "ML Engineer — Компания Б"     → /vacancy/12988
[e30] button   "Подать заявку"
       × ещё 47 карточек той же структуры
[e88] link     "Дальше"

↓ ещё ~120 элементов ниже, прокрутите
```

Замеры на живых страницах: сырой HTML страницы поиска вакансий — 1.4M токенов,
полный AX-дамп — ~48k, этот формат — **~2.6k**. Средний снапшот за все прогоны
укладывается в 4000 токенов; исключение — почтовый веб-клиент, у которого
одна страница-приложение даёт ~5.4k.

### 3.5 Пометки изменений

Список элементов приходит **целиком на каждом шаге**, а изменения с прошлого
шага показаны пометками слева:

```
    [e12] textbox   "Customer name:"  = "Иван Петров"
Δ ~ [e7]  checkbox  "Bacon" checked=true
Δ + [e91] alertdialog "Заявка отправлена"
Δ - [e22] button "Подать заявку" — исчез
```

Изначально здесь были настоящие дельты — только изменения, с экономией 90%+
на SPA. Пришлось отменить: текст состояния попадает только в текущее сообщение
и в истории не остаётся, поэтому базы для сравнения у модели нет. Подробности —
[`DECISIONS.md`](DECISIONS.md), ADR-024.

### 3.6 Стабильность refs

`ref` (`e12`) привязан к узлу, а не к порядковому номеру: реестр на стороне
страницы помнит соответствие «узел → ref» в `WeakMap`. После частичного
ре-рендера ref остаётся валидным.

**Прокрутка ref не отменяет.** Элемент, уехавший за край экрана, из списка
пропадает, но со страницы никуда не делся: ref разбирается на номер фрейма
и локальную часть, и у фрейма спрашивается, подключён ли ещё такой узел. Жив —
работаем, прокрутит Playwright. Выдуманный ref по-прежнему не проходит: он
должен быть кем-то выдан, а его узел — подключён к документу.

## 4. Ожидание стабилизации

`networkidle` бесполезен на сайтах с аналитикой и поллингом — он не наступает
никогда. Вместо него детектор покоя (`browser/js/stability.js`):

1. `MutationObserver` считает мутации DOM в скользящем окне
2. патчи `fetch` и `XMLHttpRequest` считают незавершённые запросы
3. страница «успокоилась», когда 500 мс подряд нет мутаций и нет запросов
4. потолок 8 секунд — дальше отдаём как есть с флагом `STATE unstable`, пусть
   агент сам решает, ждать ещё или действовать

Плюс встроенные actionability-проверки Playwright перед каждым кликом — они
закрывают большую часть гонок бесплатно.

## 5. Агентный цикл

`core/loop.py`. Один проход:

```
бюджет.начать_шаг()          лимит шагов и токенов; исчерпан → сворачиваемся
       ↓
снапшот страницы             полный список элементов + пометки изменений
       ↓
собрать сообщения            системный промпт (кэш) + сжатая история
                             + scratchpad + реестр сделанного
                             + текущее состояние + предупреждения
       ↓
модель выбирает ОДИН вызов   инструментов 17, план нигде не задан
       ↓
исполнить                    ошибка → текст для модели, не исключение
       ↓
записать шаг                 JSONL: токены, задержка, класс ошибки
```

Цикл заканчивается на `finish`, на исчерпании бюджета или на недоступности
модели. `ask_user` не завершает — ставит на паузу и ждёт ответа.

Три вещи, без которых цикл не работает автономно:

- **Ошибка инструмента — это результат, а не исключение.** Модель видит текст,
  который подсказывает направление, и делает следующий ход.
- **Непредусмотренное исключение перехватывается** и тоже превращается
  в результат: упавший инструмент не должен убивать прогон.
- **Ответ без вызова инструмента** возвращается модели как замечание. Иначе
  такой шаг молча пропускается, и модель повторяет ошибку бесконечно.

## 6. Инструменты

Полные контракты — [`TOOLS.md`](TOOLS.md). Коротко, 17 штук:

| Группа | Инструменты |
|---|---|
| Навигация | `goto`, `go_back`, `list_tabs`, `switch_tab`, `close_tab` |
| Взаимодействие | `click`, `type_text`, `select_option`, `press_key`, `scroll`, `upload_file` |
| Чтение | `read_page`, `find_in_page`, `screenshot` |
| Мета | `ask_user`, `remember`, `finish` |

Принципы:

- Инструменты **общего назначения**. Ни одного, специфичного для сайта или задачи.
- Цель действия задаётся **только через `ref`** из последнего снапшота. Приёма
  «передай мне селектор» нет — иначе модель начнёт их выдумывать.
- Каждый результат сопровождается свежим состоянием страницы — агент никогда
  не действует вслепую.
- Диалоги (`alert`/`confirm`) перехватываются и **не закрываются автоматически** —
  их текст уходит в снапшот, решение принимает агент.

Реестр инструментов (`tools/registry.py`) — единственный источник имён и схем.
Из него же собирается MCP-сервер (§14).

## 7. Управление контекстом

Требование задания сформулировано прямо: «нельзя просто отправлять целые
веб-страницы в контекст AI». Шесть механизмов, работающих вместе:

**1. Кэширование префикса.** Системный промпт + схемы инструментов ≈ 5k токенов,
неизменны между шагами и помечены `cache_control`. Две трети расхода прогона —
именно этот префикс, поэтому живой кэш меняет счёт почти вдвое (ADR-038).

**2. Компактный снапшот вместо разметки** (§3).

**3. Компакция истории.** Последние 3 состояния хранятся целиком; более старые
заменяются однострочником: `шаг 7: открыл письмо, тема «Скидки 70%»`. Вызовы
инструментов и их результаты сохраняются — теряется только описание страниц.

**4. Внешний scratchpad.** Инструмент `remember` пишет факт в структурированный
список, который живёт вне истории и всегда прикладывается целиком. Так найденные
данные переживают компакцию.

**5. Реестр совершённых действий.** `core/ledger.py`. Компакция уничтожает
детали шагов, поэтому вопрос «сколько заявок я уже отправил» модель по истории
восстановить не может — и ошибается. Реестр ведёт **цикл, а не модель**: после
каждого подтверждающего действия туда пишется подпись цели, и строка
«УЖЕ СДЕЛАНО: «Подать заявку» ×3» пересобирается заново на каждом шаге. Это
данные, а не воспоминание (ADR-039).

**6. Жёсткие лимиты.** `MAX_STEPS=60`, потолок входных токенов на задачу.
При 80% лимита агент получает предупреждение и переходит в режим завершения.

## 8. Продвинутый паттерн №1 — обработка ошибок и адаптация

Реализован первым, потому что без него агент не работает вообще.

Таксономия (`tools/errors.py`), каждый класс со своей стратегией:

| Ошибка | Авто-восстановление | Если не помогло |
|---|---|---|
| `StaleRef` | пересобрать снапшот, повторить один раз | вернуть свежее состояние + пояснение |
| `NotVisible` | `scroll_into_view`, подождать стабилизации | сообщить, что элемент вне области |
| `Covered` | вернуть, **что именно** перекрывает | агент сам закроет оверлей |
| `Timeout` | подождать ещё раз с увеличенным окном | отдать состояние с флагом `unstable` |
| `Navigation` | дождаться новой страницы, полный снапшот | — |
| `RateLimit` | backoff, затем следующая модель в цепочке | пауза и повтор, задачу не убиваем |

Поверх — четыре независимых детектора буксования (`core/recovery.py`), каждый
со своей диагностикой, потому что лечатся они по-разному:

- **Зацикливание.** Одно и то же действие три раза в окне из десяти шагов.
  Окно, а не подряд идущие повторы: дороже всего обходится карусель
  «клик → элемент перекрыт → Escape → тот же клик», где двух одинаковых шагов
  подряд не бывает (ADR-025, ADR-032).
- **Перекрытия.** Три за прогон означают, что агент воюет с интерфейсом вместо
  задачи. Подсказка здесь другая: не «вы повторяетесь», а «закройте панель
  и работайте с тем, что уже видно».
- **Перебор формулировок.** Четыре вызова одного инструмента подряд, ни один
  из которых не изменил страницу. Ловит то, что детектор циклов пропускает:
  «Спам», «спам», «Spam», «СПАМ» — подписи разные, результат один (ADR-039).
- **Тупик.** Отпечаток страницы (URL + состав элементов) не меняется несколько
  шагов подряд. Прокрутка в отпечаток намеренно не входит: сдвиг на десяток
  пикселей, не открывший ни одного элемента, — это не движение вперёд.

Все подсказки **возвращаются, если их проигнорировали**. Сказанная один раз
за прогон подсказка замолкает ровно тогда, когда она нужнее всего (ADR-034).

Отдельный слой — отказ самого браузера. Окно закрыли, Chrome обновился,
CDP-соединение оборвалось: снятие снапшота обёрнуто, и мёртвый браузер
завершает прогон штатно — с отчётом и накопленными фактами, как любая другая
неудача. Прогон, теряющий результат от одного упавшего окна, не измеряет
ничего (ADR-031).

## 9. Продвинутый паттерн №2 — sub-agent

Специализированный агент-экстрактор на самой дешёвой модели из доступных
(роль `extractor`).

Зачем: чтение длинной страницы — это 3–10k токенов, которые навсегда останутся
в истории основного агента. Вместо этого:

```
основной агент → read_page(ref, question="какие требования и зарплата?")
                      │
                      ▼
            ┌──────────────────────┐
            │ Extractor sub-agent  │  видит полный markdown страницы
            │ дешёвая модель       │  свой контекст, выбрасывается после
            └──────────┬───────────┘
                       ▼
основной агент ← {"salary": "250-350k", "requirements": [...]}   ~150 токенов
```

Главный контекст никогда не видит сырую страницу.

**Чем кормить читателя.** Первым делом страница прогоняется через `trafilatura`:
она вырезает статью и выбрасывает меню, подвал, баннеры. На статьях это работает
отлично, на списках — нет: со страницы результатов поиска приходило 1447 символов
из 27898, одна карточка из полусотни. Поэтому результат проверяется
на правдоподобие: если от видимого текста осталось меньше четверти, страница
не статья, и читателю уходит весь `innerText` (ADR-028). Все три сценария
задания — почта, заказ, вакансии — работают именно со списками.

## 10. Продвинутый паттерн №3 — security layer

`security/guard.py`. За флагом `--confirm-destructive` (`CONFIRM_DESTRUCTIVE=true`),
по умолчанию **выключен**: в брифинге просили не переспрашивать.

Как работает без хардкода: инструмент помечен флагом `destructive` — это про
механику («клик может отправить форму»), а не про сайт. Перед исполнением
дешёвая модель получает имя действия, аргументы и подпись цели из снапшота
и отвечает одним словом, необратимо ли оно. Если да — цикл встаёт, вопрос
уходит в UI, агент ждёт ответа. Никаких списков «опасных кнопок»,
классификация семантическая.

Три решения, которые важнее самого классификатора:

- **Отказ пользователя — это результат шага, а не конец прогона.** Модель
  получает «действие не выполнено, ответ пользователя такой-то» и ищет другой
  путь. Шаг помечается `error_kind="declined"` и попадает в статистику
  (ADR-016).
- **Отказ действует до конца прогона** и запоминается не только по подписи
  вызова, но и по подписи цели: `ref` той же кнопки между шагами меняется,
  и без второго ключа агент переспрашивал бы про одно и то же (ADR-017, ADR-039).
- **Сломавшийся предохранитель не блокирует работу.** Если классификатор
  недоступен, действие пропускается: страховка не должна становиться
  единственной точкой отказа.

## 11. LLM-роутер

Роли и модели разведены, чтобы менять цену и качество точечно:

| Роль | Прототип (free, z.ai) | Продакшен (Claude) |
|---|---|---|
| `navigator` — основной цикл | `glm-4.6v-flash` | `claude-haiku-4-5` |
| `extractor` — sub-agent | `glm-4.5-flash` | `claude-haiku-4-5` |
| `vision` — фоллбэк | `glm-4.6v-flash` | `claude-sonnet-5` |

Цепочка фоллбэка при 429/5xx: `основная модель → fallback → другой провайдер`.
Модель, ответившая «такой модели нет» или «недостаточно средств», уходит
в чёрный список на весь процесс — повторять к ней запросы бессмысленно.

Переключение на Claude — правка `.env`, кода не касается. Ключ и адрес
провайдера берутся **только** из окружения: ни одного значения по умолчанию
в коде, чтобы прогон не мог незаметно уйти не туда (ADR-036).

## 12. Vision-фоллбэк

Основной канал — DOM/AX. Скриншот вызывается агентом **явно**, когда он застрял:
canvas, картиночный UI, нестандартный виджет.

`browser/marks.py` рисует поверх скриншота пронумерованные рамки, номера
совпадают с `ref` из снапшота (Set-of-Mark). Модель говорит «жми e21» — и это
тот же ref, что в текстовом канале. Один вызов ≈ 1.5k токенов, поэтому только
по запросу.

## 13. UI, память, замеры

**UI.** FastAPI, один HTML-файл, поток событий через SSE: ход рассуждений,
вызовы инструментов, счётчик токенов и шагов, кнопка стоп. Вопросы от `ask_user`
приходят сюда же и блокируют цикл до ответа. Терминальный режим работает поверх
того же ядра: цикл принимает функцию «спросить пользователя» и обработчик
событий, а откуда они приходят — ему безразлично.

**Память между сессиями.** `core/memory.py`. Факты, накопленные через `remember`,
на выходе уезжают в JSON и подмешиваются к следующей задаче с пометкой возраста.
Предзаполнять её нельзя — туда попадает только то, что агент выяснил сам, иначе
она превращается в подсказку о сайте. На замерах выключена всегда.

**Замеры.** `evals/tasks.yaml` — шесть задач с ожидаемым результатом,
`evals/run.py` — прогон и сводка. В `tasks.yaml` конкретные сайты названы, и это
не нарушение: там записано то, что вводит пользователь. Граница проходит
по `src/`.

## 14. MCP-сервер

Инструменты живут в реестре (`tools/registry.py`), поэтому наружу они выставляются
без дублирования: MCP-сервер берёт схемы из `Tool.spec()` и маршрутизирует вызовы
через `ToolRegistry.invoke()`. Запускается флагом `--mcp`, транспорт stdio.

Смысл не в интеграции ради интеграции: это проверка того, что реестр
действительно является единственным источником правды об инструментах. Если бы
где-то в цикле были зашиты имена или схемы, обёртка бы их продублировала.

Ограничения этого режима — [`LIMITATIONS.md`](LIMITATIONS.md).

## 15. Что осознанно не делается

- **Не берём** `browser-use`, `Stagehand`, `Skyvern` — в них уже есть агентный
  цикл, то есть ровно то, что проверяет задание.
- **Не делаем** обход антибот-защиты — вместо этого настоящий браузер
  пользователя.
- **Не делаем** headless-режим.
- **Не параллелим задачи** — браузер общий, параллелить нечего.

Полный список того, что не работает или отложено, — [`LIMITATIONS.md`](LIMITATIONS.md).
